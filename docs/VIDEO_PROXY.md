## 0. 一句话结论

**不能靠「放宽白名单」支持视频，但 HitFilm 式「代理视频文件」经真机 A/B 验证值得做。**

在反馈者提供的 `aps.aup2`（309 个视频对象）上，真机 2.1.18b 连续播放整帧
**median 494.4 ms ≈ 2 fps**；禁用全部 `動画ファイル` 后降到 **42.0 ms** ——
**视频对象及其下游占 91.5%**（逐帧口径 79–84%）。
这与「寄明月 PV」正好互补：那个工程瓶颈在次合成展开（`シーン` 36 个），
这个工程 `シーン` 引用为 **0**，瓶颈就在视频素材本身。

## 2. 真实素材规格（用户向反馈者取到一条）

`IMG_2329.MOV`，206.9 MB，正好是 29 个唯一 `IMG_####.MOV` 之一（被引用 1 次）。
本机无 ffprobe/ffmpeg，直接解析 ISO BMFF atom 树：

| 项 | 值 |
| --- | --- |
| 容器 / 编码 | `qt  ` / **3840×2160 HEVC Main 8-bit Level 5.1** |
| 色彩 | `colr=nclx` primaries=1 / transfer=1 / matrix=1 → BT.709 **SDR** |
| 帧率 | **59.96 fps VFR**（stts 27 组，delta 10 / 11 → 60 与 54.545 fps 混合） |
| 时长 / 帧数 / 码率 | 35.705 s / 2141 帧 / **48.6 Mbps** |
| GOP | 39 个 I 帧 ≈ **0.92 s**，随机 seek 平均要解 ~27 帧 |
| 轨道 | 6 条：`hvc1` + `mp4a` AAC 48 kHz 立体声 + 4 条 `mebx` 元数据 |
| 方向 | `tkhd` a=d=−1 + 平移(3840,2160) = **180°**（iPhone 录制方向元数据） |

> 用户看到的「上下颠倒」来自这个矩阵，与 ProxyLayer 无关。
> 原工程有 89 个 `ローテーション(90度回転=2)` + 35 个 `回転` 负责校正。

单帧未压缩 RGBA = 31.6 MB。真机最小验证（仅 `動画ファイル` + `標準描画`，
注入 L-SMASH）稳态 **21.2 ms / median 22.8 ms ≈ 45 fps** —— 单路 4K HEVC 解码不是大头，
**79 路并发 × 0.17 s 短片段 × 0.92 s GOP 随机 seek** 才是。

## 3. 为什么不能照搬现有架构

| 约束 | 证据 |
| --- | --- |
| **成本模型相反** | 现有收益来自「一次解码原图 → 生成代理 → 之后每帧 `SourceView empty{}` 不再请求原图」。缓存键 `MakeKey(file, div, w, h)` **不含帧号**，每文件一张；视频每帧内容不同 → 无法跨帧复用，每帧仍要解码全分辨率，还多一次降采样 + `set_image_data` → 净收益为负 |
| **音频会丢** | `filter_plugin_table` 只有 `FLAG_VIDEO \| FLAG_INPUT`，`func_proc_audio = nullptr`；`動画ファイル` 带 `音声付き=1` |
| **帧号语义** | 当前用无帧号 `get_image_file_cache(file)`。SDK 有 `get_video_file_cache(file, track, frame)` / `_by_time(...)` / `get_video_file_info(VIDEO_INFO)`，但要重写整条渲染路径：时间映射、track、VFR、逐帧 LRU 与内存配额 |
| **像素格式** | `INPUT_PIXEL_FORMAT::YUY2 / YC48` 已被现有代码拒绝，视频常用 YUV 输入 |
| **导出 / 还原** | 导出闸门现在只回 L0 原图；视频要回「原始 `動画ファイル` 逐帧」。OFF 还原要保存 8 个参数（`再生位置 / 再生速度 / トラック / ループ再生 / 音声付き / YUV / fps調整 / ファイル`），现在只存 2 个元数据 |
| **宿主前提** | `aviutl2.txt:391`「VRAM 数据缓存只有静止画是缓存对象」—— ProxyLayer 针对「静止画被反复解码」，对视频本来不成立 |

## 4. 真机四组 A/B（2026-11-20，AviUtl2 2.1.18b）

### 4.1 方法

- **路径重定向 + NTFS 硬链接**：32 个唯一视频路径 → 32 个硬链接（物理仅一份 206 MB，
  路径不同 ⇒ 宿主缓存键不同），图片替身指本地 `proxy-grid-2048.png`。
  只改 324 行 `ファイル=`，其余 46,663 行逐字节不变；派生到隔离目录，**原工程全程只读**。
- 4 组：`A-redirect` 基线 / `B-no-video`（309 个 `effect.disable=1`）/
  `C-no-audio`（308 个 `音声付き=0`）/ `D-no-scripts`（301 处重脚本 `effect.disable=1`）。
- 每组独立宿主进程 → 独占一个带时间戳的日志文件，天然切片。
  采集**连续播放**（SPACE 16 s）与**逐帧**（RIGHT × 25，不依赖播放快捷键）两个窗口。
- 真机启动会弹 **「failed load some objects」模态对话框**（缺 `ParallelCam` / `SVG` /
  `quantizer.aux2対象外` / `AutoClipping_S` 等第三方效果），它会吞掉 SPACE 并阻断 WM_CLOSE；
  脚本先消除对话框再测量。误差对 4 组一致，差值仍可比。
- `FileLogLevel` 本来就是 1（VERBOSE），**本次未改 ini**。

### 4.2 结果（同一帧区间 519→547）

| 变体 | PLAY mean | PLAY median | STEP mean | STEP median | n(STEP) |
| --- | --- | --- | --- | --- | --- |
| **A-redirect** | **494.4 ms** | 504.5 | **284.5 ms** | 181.0 | 40 |
| B-no-video | 42.0 | 36.2 | 41.0 | 37.3 | 189 |
| C-no-audio | 412.3 | 391.3 | 252.3 | 177.6 | 44 |
| D-no-scripts | 316.9 | 231.7 | 203.7 | 101.6 | 49 |

| 归因 | PLAY 口径 | STEP 口径（trimmed mean / median） | 判断 |
| --- | --- | --- | --- |
| **视频对象及其下游 A−B** | **452.4 ms = 91.5%** | **201.6 ms = 84.1% / 79.4%** | **主瓶颈，四种口径一致** |
| 重脚本效果链 A−D | 177.5 ms = 35.9% | 91.4 ms = 38.2% / 43.9% | 视频对象下游的子集，不可与 A−B 相加 |
| 音轨混流 A−C | 82.1 ms = 16.6% | 43.5 ms = 18.2% / 1.9% | 不稳定，主要落在长尾 |

A 基线 ≈ **2.02 fps**（PLAY）/ **3.51 fps**（STEP），场景要求 60 fps。

### 4.3 隔离夹具的两次失败（数据作废，留作踩坑记录）

1. 夹具默认 seed 是 **2.1.15**，只注册 7 个输入插件（图片 / WIC / AVI / Wave / 模型 / 文字 / 图形），
   **没有 MOV/HEVC 解码器** → 第一次最小验证「216 帧 median 16 ms」是空场景。
2. 注入真机 `C:\ProgramData\aviutl2\Plugin\lwinput.aui2`（25.9 MB，L-SMASH Works）
   + 换 2.1.17 seed 后能解出真实画面，但 seed 缺 `data/` 骨架导致 `FileLogLevel` 写不进去，
   且缺第三方脚本、播放只采到缓存后的 72 ms 轻帧（真实重帧 1379 / 2028 ms）。
   另外 profile 必须删掉 `expectedManifestVersion`（seed 父目录无 `manifest.json`）。

**最终验证必须在真机 2.1.18b 上做**：那里有 `lwinput.aui2` 与 368 个脚本
（工程用到的 25 种自定义效果里 18 种可在内容中找到）。

## 5. 修正后的方向：HitFilm 式代理视频文件

§3 的「净收益为负」只针对**现有架构**。真正的收益来自两点：

1. **降低解码分辨率**：4K HEVC 48.6 Mbps → 1080p 低码率代理。
   工程中 257 个 `拡大率=50%`，4K 素材本来就显示成 1920×1080，
   所以 `div=2` 代理在预览里**画质无损**（与图片代理不同的重要结论）。
2. **缩短 GOP**：转码成全 I 帧 / 极短 GOP，把「随机 seek 平均解 27 帧」压到 1 帧。
   这正对上 median 0.17 s 的短片段与 79 路并发。
3. 额外红利：134 个 `再生速度=0.00` 冻结帧本来就能跨帧复用。

架构与 [`PRERENDER.md`](PRERENDER.md) 共用：内容指纹（改动即失效）、
跨帧缓存、导出硬闸（`EDIT_STATE_SAVE` 强制回原文件），
但产物是**落盘的代理视频文件**，并由自定义 `INPUT_PLUGIN_TABLE::func_read_video`
按帧提供，而不是 `CACHE_IMAGE` 里的单张纹理。

### 仍待解决的硬问题

- 音频：代理文件必须保留 AAC 音轨，或让宿主继续从原文件取音频而只代理视频轨。
- VFR：60 / 54.545 混合帧率下，代理与原文件的帧号映射需要逐帧时间索引。
- 失效粒度：一个素材被 293 个 `IMG_` 引用中的多个对象以不同 `再生位置` 切片段使用，
  指纹应按「原文件」而非「对象」计算。
- 元数据轨：4 条 `mebx` 是否需要透传（陀螺仪等），先按丢弃处理并验证画面等价。

## 6. 建议的下一步与验收门槛

- **P0（已完成）**：真机 A/B，确认瓶颈归属 ≥ 70% 落在视频对象。**实测 79–92%，通过。**
- **P1**：单个素材的代理视频原型（离线转码 → 自定义输入插件按帧读 → 导出硬闸）。
  验收：同一帧逐像素 A/B 等价、播放帧时间显著下降、导出与原文件一致。
- **P2**：并发路数扩展（10 → 79）与内存/句柄配额。
- **P3**：内容指纹失效、多片段 `再生位置` 映射、UI 开关与进度提示。

### 优先级建议

两个方向针对不同工程、互不替代：

| 工程 | 瓶颈 | 优先方向 |
| --- | --- | --- |
| 寄明月 PV（图片 + 36 个 `シーン`） | 次合成展开，整帧 1608 ms，插件仅 0.18% | `PRERENDER.md` |
| `aps.aup2`（309 视频，`シーン`=0） | 视频对象 79–92% | 本文 |

若以「让更多用户立刻受益」为准，视频工程的绝对卡顿（2 fps）比 PV 更严重，
且素材规格单一（4K60 iPhone MOV），**建议先做视频代理 P1**。
