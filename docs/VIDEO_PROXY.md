## 3. 为什么不能照搬现有架构

| 约束 | 证据 |
| --- | --- |
| **成本模型相反** | 现有收益来自「一次解码原图 → 生成代理 → 之后每帧 `SourceView empty{}` 不再请求原图」。缓存键 `MakeKey(file, div, w, h)` **不含帧号**，每文件一张；视频每帧内容不同 → 无法跨帧复用，每帧仍要解码全分辨率，还多一次降采样 + `set_image_data` → 净收益为负 |
| **音频会丢** | `filter_plugin_table` 只有 `FLAG_VIDEO \| FLAG_INPUT`，`func_proc_audio = nullptr`；`動画ファイル` 带 `音声付き=1` |
| **帧号语义** | 当前用无帧号 `get_image_file_cache(file)`。SDK 有 `get_video_file_cache(file, track, frame)` / `_by_time(...)` / `get_video_file_info(VIDEO_INFO)`，但要重写整条渲染路径：时间映射、track、VFR、逐帧 LRU 与内存配额 |
| **像素格式** | `INPUT_PIXEL_FORMAT::YUY2 / YC48` 已被现有代码拒绝，视频常用 YUV 输入 |
| **导出 / 还原** | 导出闸门现在只回 L0 原图；视频要回「原始 `動画ファイル` 逐帧」。OFF 还原要保存 8 个参数（`再生位置 / 再生速度 / トラック / ループ再生 / 音声付き / YUV / fps調整 / ファイル`），现在只存 2 个元数据 |
| **宿主前提** | `aviutl2.txt:391`「VRAM 数据缓存只有静止画是缓存对象」—— ProxyLayer 针对「静止画被反复解码」，对视频本来不成立 |

## 5. P1 原型实测（2026-11-20）：收益来自「降分辨率」，不是 GOP

> ⚠️ **本节推翻了 §4 之前的推测**。实测前曾判断「0.92 s GOP 的随机 seek 是主瓶颈」，
> 转码 A/B 证明该判断不成立。以下为修正后的结论。

用真机自带的 `exe_files/QSVEncC/x64/QSVEncC64.exe`（8.38，Intel QSV 硬件编解码）
把 `IMG_2329.MOV` 转成 4 个代理变体，每个变体都用 **32 个不同路径（NTFS 硬链接）**
派生工程，保持宿主缓存键数量一致、单一变量。

| 变体 | 尺寸 / 编码 | GOP | 大小 | PLAY mean | STEP mean | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| A 基线 | 3840×2160 HEVC 48.6 Mbps | 0.92 s | 207 MB | 496.0 ms | 354.7 ms | — |
| E 4K 全I帧 | 3840×2160 H.264 100 Mbps | 1 | 430 MB | 593.3 ms | 545.5 ms | **反而更慢** |
| H 4K 轻量 | 3840×2160 H.264 5 Mbps | 60 | 21 MB | 601.4 ms | 486.2 ms | **反而更慢** |
| F 1080p 全I帧 | 1920×1080 H.264 56 Mbps | 1 | 240 MB | 254.2 ms | 127.1 ms | 有效但不如长 GOP |
| **G 1080p 长GOP** | 1920×1080 H.264 6.6 Mbps | 60 | **29 MB** | **226.4 ms** | **109.2 ms** | **最优** |

**结论**：全 I 帧 4K 变体慢 20–54%（码率 100 Mbps > 原 48.6），
4K 低码率变体（21 MB / 5 Mbps）也慢 —— **只要像素尺寸不变就没有收益**。
真正的成本是 4K 帧缓冲（31.6 MB/帧）的解码 / 转换 / 上传。
`--gop-len 60 --cqp 32 --output-res 1920x1080 --audio-copy` 是最终参数。

### 5.1 降分辨率必须同步补偿 `拡大率`

代理尺寸变小 → 宿主读到的 `INPUT_INFO` 变成 1920×1080 → 工程里 257 个
`拡大率=50%` 会把画面缩成一半。单对象工程（一个 `動画ファイル` + `標準描画`）像素级 A/B，
预览区 ROI 790×410：

| 组合 | 平均绝对差 | 差异>30 的像素 | 判定 |
| --- | --- | --- | --- |
| 原片 4K + `拡大率=50%` | 0（基准） | — | — |
| 1080p 代理 + `拡大率=50%` | 72.76 | 59.2% | 画面缩成一小块 |
| **1080p 代理 + `拡大率=100%`** | **2.34** | **0.0%** | **几乎逐像素等价** |

并排截图 `video-ab/real-runs/equiv/equiv-compare.png` 可肉眼复核。

### 5.2 P1 原型工具链（`ProxyLayer/host-test/video-ab/make_video_proxy.py`）

纯离线脚本、不改任何 DLL / 语言包 / ini，实现 HitFilm 契约的四段：

```
transcode   QSVEncC 转码 + 生成 .plv.json（原/代理路径、尺寸比、内容指纹）
convert     按 [N.M] 块精确识别视频对象：ファイル → 代理路径，拡大率 ×2，
            并写入 元の動画ファイル / 元の拡大率 / ProxyLayer動画プロキシ
export      生成导出用工程副本（原素材 + 原拡大率）
restore     从元数据重建工程
verify      指纹变化 → STALE，需重新转码
```

| 验收项 | 结果 |
| --- | --- |
| 识别视频对象 | **308 个**（另 9 条 `.MOV` 属 `画像ファイル` / `音声波形表示`，正确跳过） |
| `ファイル` 重定向 | 308 行 → **32 个不同代理路径**（硬链接，物理仅一份 29 MB） |
| `拡大率` 补偿 | 308 行 ×2，**只作用于视频对象** |
| export / restore | **逐字节等于原工程**（795,417 B），3 个元数据项残留 0 |
| 内容指纹 | 记录/现值一致 → VALID |
| 同批次 A vs J2 | PLAY **473.4 → 204.6 ms（56.8%）**；STEP **272.5 → 118.6 ms（56.5%）** |
| 帧推进 | 17 → 41 帧（PLAY）、41 → 73 帧（STEP） |

> **踩坑**：第一版工具把 308 个对象全指向**同一个**代理路径，比 32 个不同路径慢约 30%
> （推断宿主按文件串行化解码 / 缓存锁竞争）。必须「每个原始路径对应一个硬链接」。

### 5.3 导出硬闸（P1 原型形态）

`plugin2.h:734` 的原文是「編集が出来ない場合(出力中やドラッグ編集中等)に失敗します」——
输出中调用 `call_edit_section()` 会**失败**，并非「明确禁止」；头文件里真正写
「利用出来ません」的是事件回调(`:1201`)与 `RegisterPlugin` 内(`:726`)。
因此 P1 采用**导出用工程副本**：输出前打开 `*.export.aup2`（与原工程逐字节相同）→ 无损。
自动切换在 P2 改走 **A′ 路线**（见 §5.4）：在 F9 到达、宿主仍是 `EDIT_STATE_EDIT`
时把工程批量还原成原始素材，输出结束后自动切回代理，**不需要自定义输入插件**。
原先核对过的 `register_input_plugin()` / `lwinput.aui2` 转发 /
`FLAG_TIME_TO_FRAME` 等零件暂时不用，保留为后续可选方案。

### 5.4 P2 / A′：导出前自动还原工程（真机四轮验证）

**为什么图片不需要拦截、视频需要**：图片代理是「渲染时换数据源」——工程零改动，
滤镜逐帧读 `get_edit_state()` 即可回 L0（`ProxyLayer.cpp` 里一行 `if (saving) div=1`）。
视频代理是「工程里换了文件」——P1 改了 `ファイル` 与 `拡大率` ×2，导出必须写回，
而输出中 `call_edit_section()` 会失败，所以必须抢在输出开始前的时间窗。

**探针（真机 2.1.18b，2026-11-20）**：隔离 DLL 在 `WM_KEYDOWN VK_F9` 到达 UI 线程时
读到 `EDIT_STATE_EDIT(0)`，`call_edit_section()` 返回 1、回调执行、`EDIT_SECTION::info`
可用 ⇒ 时间窗成立。报告见工作区
`ProxyLayer/host-test/p2-probe/P2_PROBE_REPORT.md`（仓库外）。
真机只加载 `module.ini` 里登记 `trust=1` 的 `.aux2`，探针临时登记后已逐字节恢复。

**四轮迭代（每轮都临时替换真机 DLL、跑完逐字节恢复 + SHA256 校验）**：

| 轮次 | 结果 | 判定 |
| --- | --- | --- |
| 1 | `found=0` | 未知原因，加诊断日志 |
| 2 | `objects=1 video=1 file=1 scale=1`、`metaFile=0 metaScale=0` | **宿主加载 `.aup2` 时丢弃未知键**，`元の動画ファイル` / `元の拡大率` 到不了 SDK |
| 3 | 改为直接解析工程文本：`projectMeta ok=1 total=1`、`found=1 changed=1`（16 ms） | 识别通道打通 |
| 4 | `readback file=1 scale=1`、`verified=1 mismatch=0 changed=1` | 写回**确实落地**，不只是 API 返回 true |

**v2 识别通道**：`EDIT_SECTION::get_project_file(g_edit)` →
`PROJECT_FILE::get_project_file_path()`（`plugin2.h:1001`）拿到工程路径，
插件直接读 UTF-8 `.aup2` 文本，按 `[scene.N]` / `[N]` / `[N.M]` 解析
`layer` / `frame` / `ファイル` / `元の動画ファイル` / `拡大率` / `元の拡大率`，
按 `(layer, frame)` 用 `find_object()` 定位对象写回。拿到的是**用户真实原素材路径**
（优于 sidecar 里的沙箱副本）。无元数据的普通工程 `found=0`，F9 完全 no-op。

**当前状态（不宣称完成）**：F9 拦截 → 全场景还原 → SDK 读回一致的闭环已真机验证；
以下仍未实跑，列为下一阶段验收项。
